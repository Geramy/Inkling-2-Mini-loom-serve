# How the Inkling 2 Mini Loom programs are made

This file is written by hand. `README.md`, `REPORT.md` and `info.json` are generated by the loom-skills card tools and are never edited. Read this file to understand, rebuild or change the package.

## 1. The model and why the programs are hand-written

Inkling 2 Mini (arch `inkling2_loop` in the GGUF) is a looped mixture-of-experts text model:

- 24 physical layers, hidden size 2304, 24 query heads and 8 KV heads of size 128. Layers 6 to 17 run 3 times, so one token makes 48 layer visits. Weights are shared between the passes. KV and conv state are separate for each visit.
- 20 of the 24 layers use a local window of 1024 tokens. Layers 5, 11, 17 and 23 are global, so 8 of the 48 visits are global.
- Attention has no RoPE. Position enters through 16 relative-bias channels per head (a table of 1024 distances) and a per-token, per-head softmax sink.
- Each visit uses short convolutions (kernel 4) on K, V and the two residual branches, and an attention-residual mix over stored block states. Passes 2 and 3 add a message and controller mix.
- 128 experts, 8 used per token, SiTU activation, a per-expert scale that applies on every visit.
- Tensor types in the Q4_K_XL file: NVFP4 experts, Q8_0 attention, embedding and lm_head, BF16 sink and dynamic-conv projections, F32 router and controllers. In the Q8_K_XL file everything that is not an NVFP4 expert is BF16 (router and small tensors F32). Neither file has K-quants.

No generator in the loom-skills starter covers this layout (loop, attention-residual mixing, NVFP4, relative bias with sinks). The programs are therefore written by hand as a catalog-style package. The model is described in the source repository in `docs/ARCHITECTURE.md`; every formula there was checked against llama.cpp.

## 3. Tokenizer

`tokenizer.json` is generated from the GGUF (byte-level BPE, 200058 tokens, 424,413 merges, the GPT-4o style pre-tokenizer of the model). `scripts/gen_tokenizer.py` writes the file from the GGUF. `scripts/chat_tokenizer.py` then sets 12 structure tokens to `special: false` (`<|message_user|>`, `<|message_model|>`, `<|message_system|>`, `<|message_tool|>`, `<|content_text|>`, `<|content_image|>`, `<|content_thinking|>`, `<|content_xml|>`, `<|content_tool_error|>`, `<|content_invoke_tool_json|>`, `<|content_invoke_tool_text|>`, `<|end_message|>`). Reason: loom-serve decodes output with special tokens skipped, and the chat control code must see these tokens in the text to find thinking, content and tool calls. The end token `<|content_model_end_sampling|>` (id 200006) stays special. `llm_config.json` lists the same 12 tokens as `nonspecial_tokens`. `scripts/tokenizer_check.py` compares loom-serve tokenization with `llama-tokenize` on the same GGUF.

## 4. Program anatomy (`program/`)

Prepare, storage and config
- `prepare.loom` declares the stage catalog (one stage per host shape bucket) and the prepare results. `storage.loom` has the state geometry. `config.loom` and `card_defaults.loom` declare the config keys and their defaults. `dispatch/targets.loom` declares the target families (`gfx11-generic`, `gfx12-generic`).

Dispatch (`dispatch/`)
- `model.loom`: command `inkling_model` (embed, schedule, head). `layer.loom`: command `inkling_visit(layer, visit, pass)` with the launch list of one visit. `visit.loom`: pure helpers (global or local, loop pass, controller or not, expert weight type). `spans.loom`: span table and token map. The schedule is unrolled at plan time: layers 0 to 5, three passes of layers 6 to 17, layers 18 to 23, then the head.
- Each kernel step is a hook, one `command.def` with the same 20 buffers. `hooks_dense.loom`, `hooks_attn.loom`, `hooks_mix.loom` and `hooks_experts.loom` are generated by `scripts/gen_hooks.py` in the source repository. To change a hook, edit the generator and run it again. Do not edit the generated files.
- `capture.loom` (capture config) and `stub_debug.loom` (an empty debug hook) belong to the capture route (section 7). They add no work to a normal request.

Kernels (`kernel/`, plain Loom kernels, all assume wave 32)
- `experts/`: router (F32 GEMV and fused top-8), route grouping, gate and up with scale and SiTU, down, combine, and WMMA variants for prefill. NVFP4 weights are decoded in the kernel (`lib/inkling/nvfp4.loom`: 36 bytes per 64 values, four UE4M3 scales and E2M1 nibbles).
- `attn/`: prep (convs, L2 clips, tau, KV append), tile attention with relative bias and sink, merge of the decode splits (with sink and gate), conv commit, KV append.
- `dense/`: norms, embedding, GEMV and GEMM for Q8_0, BF16 and F32 weights, and the head (selection, norm, lm_head, soft cap 30).
- `mix/`: attention-residual mix, loop message and controllers, post-convolution with residual.

Libraries (`lib/`)
- `lib/inkling/`: our motifs. Matrix operations are template families. Each template (for example `inkling.dense.mma.k64_2x2`) has a portable provider (priority 1) and a provider for each tuned arch (`target(@inkling_dense_gfx11)`, `target(@inkling_dense_gfx12)`, priority 20) that uses the WMMA layout of that arch.
- `lib/vendor/`: copied from ROCm/hrx-loom-library, tag v0.2.0 (MIT; the copies build and run on hrx-loom 0.3.0 without change): epoch, storage, packet, feedback, span, q8_0, sampling, random. `NOTICE` lists every copy and edit.
- `lib/media_stub.loom`: our stub for the two media functions that `epoch.loom` declares.

Control (`control/`)
- `chat.loom`: the text-service chat exports (template, request options, effort, tool-call parsing, output channels). `chat_json.loom`: canonical JSON writer (sorted keys, compact). `chat_sampler.loom`: device sampler for the options record. `identity.loom`: the model name export. The full policy is in the source repository `docs/CHAT_POLICY.md`.

## 5. State per sequence

- Global KV: 8 planes (the global visits), pages of 64 tokens (262,144 bytes), 4096 bytes per token per plane (K and V in F16). So 32 KiB per token in total. Pages come from one pool shared by all rows.
- Local KV: one ring of 1024 tokens for each of the 40 local visits (4 MiB each).
- Conv state: 3 rows of 6656 F32 values for each of the 48 visits.
- Attention-residual blocks and the loop bank live only inside one token step.
- A slot (ring and conv state of one row) is 171,608,576 bytes. 4 rows and 4 checkpoints give 12 slots (2.0 GiB).

## 6. Per-arch tuning

Arch-dependent choices are data, not code paths. The program never asks for the device name. Each tuned value is a template (`template.decl`) with a portable default provider and one provider per tuned target. The live device selects the matching provider when the command is planned, and the result is passed to the kernel as a launch scalar. Rows that depend on the shape (live row count, split counts) are set in `prepare` with `config_i64`. Card `config` values are the override path for values that are not arch data (the weight type of the dense tensors, `inkling.dense_type`). A wrong target alias silently selects the portable default, so every row is tested on both GPUs. The source repository `docs/TUNE_ROUTE.md` has the test and the limits.

## 7. How each part was checked

- Oracle: mainline llama.cpp built for CPU only (master `418fe97` plus the cherry-picked fix of PR 32704, which adds `inkling2_loop`), with F32 KV. A dump tool writes reference tensors for prompts A, B and C.
- Kernel tests: every kernel has tests against numpy references and against oracle tensors, run on both GPUs (33 of 33 targets pass with the wave 2 programs, evidence in `info.json`). The head chain and the lm_head cases include the oracle's `result_norm` and `result_output`.
- Capture route (checked on hrx-loom 0.2.0; the `sequence` deployment does not register on 0.3.0 and needs a port to the new text epoch contract): a debug deployment (`kind: sequence`) returns the chosen tensor of any visit. It was used to compare the embedding, norm, mix, attention and expert outputs with the oracle layer by layer, including chunked prefill.
- Golden and compare: `golden.py` records greedy tokens and top-5 log-probs from the CPU llama.cpp server. `compare.py` accepts a divergence only if it is a near-tie. Result on both GPUs: golden, compare and consistency pass (R9700: 14 prompts at dev level, 7 full matches, max gap 0.582 nat; the full set of 23 prompts 12 full matches, 0 bad. 8060S: 14 prompts, 9 full matches, max gap 0.296; 23 prompts 14 full matches, max gap 0.461, 0 bad). The gaps are near-ties at which the greedy text leaves the CPU reference; the numbers differ from the first build because reordered float sums flip a few such ties.
- Agent gate: a multi-turn tool-calling loop with exact prompt rendering, history reuse and valid calls. It passes with and without `name` in the tool messages (section 13).
- Context admission: a request of nearly the whole preset context is admitted and completes (131072 context, one request of 130972 tokens: 174 s on the R9700, 591 s on the 8060S after the gate run; a clean single request was 120 s and 343 s with wave 1).
- Chat glue: 101 template cases, 101 echo cases, 29 output and 37 option checks per GPU, against jinja2 and llama.cpp rendering.
- Sampling gate: fails on both GPUs. The script expects a request without sampling fields to be greedy, and this package defaults to temperature 1.0 (the model's recommended sampling). Equivalent checks for a sampling default (temperature 0 repeats, `top_k 1` and a tiny `top_p` equal temperature 0, equal seeds repeat) pass 4 of 4 on both GPUs. The 200-draw distribution check cannot run because the first token is a structure token.
- Performance is measured against a CPU llama.cpp (12 threads, F32 KV) because no GPU llama.cpp build was available. It is a reference, not a competitor.

## 8. How to rebuild

These scripts live in the source repository, not in this tree. Placeholders: `<src>` source repository, `<skills>` loom-skills checkout, `<gguf>` directory with the two GGUF files, `<snap>` directory with `Mainline_Support/<name>.gguf_file` links to them.

1. `scripts/publish_build.py --cfg cfg.json --skills <skills> --gguf-dir <gguf>`: reads `package/` (the working copy of the programs and `card.json`) and writes this tree: `model.json` with the four presets, `program/`, `weights.loom`, `tokenizer.json`, `LICENSE`, `NOTICE`, `.gitattributes`. `cfg.json` comes from the skills' `inspect_gguf.py`. The script checks that the presets equal `card.json` except context, transient memory and workload text.
2. `scripts/make_llm_config.py --publish <tree> --cfg cfg.json --skills <skills>`: writes `llm_config.json` (GGUF geometry, loop plan, memory fit, SDK pin, `kit/chat_block.json` as the chat block).
3. `scripts/publish_lock.sh <tree> <snap>`: runs `loom-fetch --update-lock --all-variants` and writes `model.json.lock`.
4. `scripts/scrub_check.sh <tree>`: fails if the tree names a host, user or local path.
5. `scripts/make_card.sh <tree>`: runs the measurement evidence (`ev_*.json` from `make_info.py gates|perf|roofline`, made on the machine that measured) through `make_info.py build` and `render_card.py`, then validates the result. It writes `info.json`, `README.md` and `REPORT.md`. It needs the evidence per GPU and the memory figure of the chat preset.

Evidence inputs: the gate results, the kernel-test log, the performance logs (`perf.py`, `c4_steady.py`) and the roofline tables. The roofline comes from `scripts/roofline_inkling.py` because the skills' `roofline.py` does not model the loop (it gives 2.3 GB per token instead of 4.0 GB).

## 9. How to run

```bash
pipx install "hrx-loom[hf]==0.3.0"
loom-fetch <tree>/model.json --preset chat-r9700 --materialize=copy --output=<dir> --origin checkpoint=<snap>
loom-serve --model=<dir> '--device=amdgpu://?completion_spin_ns=4294967295' --pool_backing=fixed
```

- On a two-GPU host the device must be named (`amdgpu://<id>?completion_spin_ns=4294967295`, ids from `loom-run --list_devices=amdgpu`) because the generated quick start in `README.md` uses the unnamed device URI, which can select the wrong GPU.
- Use the preset of your GPU: `chat` (8060S) or `chat-r9700` (R9700); `chat-q8` and `chat-q8-r9700` for Q8_K_XL. A fetched directory holds only the preset you selected. Without `--origin`, `loom-fetch` downloads the GGUF from Hugging Face.
- The generated `README.md` gives `--parameter_mode=preload` for the R9700 (a rule of the card tool for hrx-loom 0.2.0). hrx-loom 0.3.0 rejects that value (`loom-serve` accepts `file` or `direct`): leave the flag out, as in the command above. `--pool_backing=fixed` was used for every measurement.
- Model id: `thinkingmachines/Inkling-2-Mini`. Endpoint `/v1/chat/completions` (OpenAI style, streaming or not).
- The model thinks first (default effort `high`): the reasoning is in `reasoning_content`. Give `max_tokens` enough room. Set the effort with `reasoning_effort` (none, minimal, low, medium, high, xhigh, max, or a number from 0 to 0.99) or `chat_template_kwargs`.
- Start one server per GPU. A second model on the same GPU fails with `RESOURCE_EXHAUSTED`.

## 10. Known limits

- Prefill stages: the Q4 presets use `prefill_capacity` 2048 (stages of up to 2048 tokens, longer prompts are split by the service). The Q8 presets stay at 512 because the larger capacity was not measured for Q8; the programs are the same, so a Q8 preset can raise it after a measurement. The routes kernel no longer limits a stage to 512 tokens (the rank store is gone and a second counting pass places each route), so the old hang with stages above 512 does not occur. Stages up to 2048 were tested (kernel tests, greedy replies and layer checks with chunkings 1, 3 and 512 plus rest). Values above 2048 were not tested. A larger capacity needs more workspace (about 0.4 GB at 2048 by an earlier measurement; the measured total is in the context paragraph above) and a longer first compile on a cold kernel cache. After any GPU hang the next start fails with `DATA_LOSS` for about two minutes.
- At most 256 spans per stage (attention kernels); 4 rows.
- A tool message without `name` is accepted (section 13). The runtime still rejects `function.arguments` given as a JSON object and a tool call without `type` (HTTP 400): those checks run before the package policy.
- Images, audio and video are not supported (text parts only). There is no vision projector and no speculative decoding.
- Unsupported request fields are rejected with HTTP 400 (`logprobs`, `top_logprobs`, `stop`, `n` above 1, penalties other than the neutral value).
- The served context is below the native 1,048,576 (131072 for Q4 presets, 32768 for Q8 presets). Attention makes very long prefill slow.
- Near-ties in routing and output can flip against llama.cpp, so greedy text matches for many tokens and then may differ.
- Performance numbers on the card compare with a CPU llama.cpp only. There are no ROCm or Vulkan llama.cpp numbers.
- The generated `README.md` says "greedy decoding only" in its sampling row, and the sampling gate in `info.json` is failed. Both come from the skills' check, which assumes a greedy default. This server samples: the default temperature is 1.0 (the recommendation of the model), and `temperature`, `top_p`, `top_k` and `seed` are supported. The supplementary check `scripts/sampling_supplement.py` passes 4 of 4 on both GPUs. The README text is generated and is not edited by hand.

## 12. Performance structure and results (waves 1 and 2)

Four changes in the programs raised the speed after the first working build. All are in the source files named in section 4; none changes the model math beyond float summation order.

- Experts, prefill: the WMMA gate/up and down kernels use 64-route tiles (before: 32). The routes kernel has no per-workgroup rank store any more, so it is valid for any stage size (before: at most 512 tokens). With that, the Q4 presets set `prefill_capacity` 2048 and the weights are read once per 2048 tokens instead of once per 512.
- Decode launch fusions: the conv commit runs inside the next mix launch (95 launches less per token), the mix launch also computes the norm for local attention and FFN visits without a controller (about 43 less), and one column-norm launch replaces the three input-norm launches (about 56 less).
- Long-context decode attention: the number of splits is chosen from the context length at run time (at most 64 per visit; the block count per split is per-arch data), the K and V stage loop is unrolled, and workgroup memory is 32000 bytes (four workgroups per compute unit).
- Sampler: the device sampler is three launches (statistics, partial sums, draw) with 128 workgroups per row, instead of one workgroup (195 us to about 7 us). The draws are the same as before (checked on 20,000 tokens).

Measured on the published route (median of 3 fresh servers per GPU, Q4_K_XL, `perf.py` rows, tok/s; before in brackets):

| | decode short | decode 32k | prefill 2k | prefill 8k | prefill 32k | 4 streams |
|---|---|---|---|---|---|---|
| R9700 | 90.2 (85.9) | 71.3 (67.0) | 2996 (2075) | 3092 (1920) | 2242 (1401) | 218.9 (214.2) |
| 8060S | 39.7 (38.6) | 29.7 (27.5) | 1033 (823) | 1051 (786) | 812 (595) | 89.0 (86.6) |

A request of 130972 tokens (the Q4 preset context) completes in 120 s on the R9700 and 343 s on the 8060S (183 s and 443 s before). The speed of the CPU reference is in the card (`README.md`, `REPORT.md`).

Wave 2 (on hrx-loom 0.3.0) adds seven changes. Each is in the files named in section 4.

- Attention front end: the q, k, v, gate and rel projections run as one grouped GEMV (shared input), and the attention prep, K/V append and conv commit are fused. The merge of split attention is one launch (about 336 launches less per token).
- Experts, decode: the gate/up and down kernels are software pipelined (NVFP4 fast path). On the 8060S the down kernel is a wave64 kernel (`kernel/experts/down_w64.loom`, `lib/inkling/targets_w64.loom`); the R9700 does not use it.
- Controllers and router: the message mix is folded into the controller launch, the router selects the top experts with subgroup ballots, and the router and routes run as one decode launch (about 144 launches less per token).
- The tuned values are per-arch data as before; the results are bit-equal in the kernel tests and give the same greedy text as wave 1 (prompts A, B, C and documents of 8k and 32k tokens, both GPUs).
- Grouped projection grid: the grouped attention projection GEMV has its own workgroup-per-unit tune value (7 on gfx1201, 4 on gfx1151), which cuts the tail of the launch on the R9700 (decode +2.3 to +2.8 percent; same arithmetic, bitwise equal outputs).
- Small decode kernels without waits on branches: a value that leaves an `scf.if` makes the compiler wait for its load, so a loop that loads through `scf.if` issues one load, waits, then issues the next. In `mix_states`, the attention tile, the attention prep conv, the norms (width 2304), `conv_res` and the router (one-token direct route table) the branch now sits outside the loop or both sides load and a select picks one, with the same arithmetic order (bitwise equal results). The expert combine is folded into the post-FFN conv/residual kernel for one-token steps (`inkling_conv_res_combine`), and the attention tile prefill mode is not launched for one-token steps. A decode step has 786 launches instead of 882.
- Experts matrix path pipelined (prefill): the NVFP4 branch of the gate/up and down matrix kernels loads the next K block (weight words and activation vectors) while the matrix operations of the current block run, instead of load, wait, compute per block. `router_logits` loads x without a branch per load, and the controller apply step issues its loads before the liveness guard. Same decoded values and matrix operation order, so results are bitwise equal; prefill 2k +11 percent (R9700) and +14 percent (8060S), decode unchanged within noise.

Measured on the published route (median of 3 serialized fresh servers per GPU, one GPU at a time, Q4_K_XL, `perf.py` rows, tok/s; wave 1 in brackets):

| R9700 | 106.4 (90.2) | 97.6 (83.2) | 94.0 (80.3) | 83.1 (71.3) | 3061 (2576) | 3634 (2996) | 3812 (3092) | 3632 (2801) | 3205 (2242) | 235.1 (218.9) |

## 13. Chat behaviour: prefix cache and tool calls

- Prefix cache: all four presets set `prefix_cache_capacity` 16 (the memory hints include 0.17 GB per endpoint; `transient_bytes` is 10.8 GB for Q4 and 6.4 GB for Q8). A follow-up request that shares a prefix with an earlier prompt reuses the state at the last multiple of `prefill_capacity` (2048 for Q4, 512 for Q8); only the rest is computed. Example, R9700, a 4,823 token follow-up: 4,096 tokens cached, first token after 0.34 s (cold 1.4 s). This works when the client does not send `reasoning_content` back. Prompts shorter than one chunk get no hit. The peak memory on the R9700 with 16 endpoints was 27.6 GB for Q4 (24.9 GB before) and 29.2 GB for Q8; pool pressure reclaims cache entries and no request failed. The Q8 presets and the 8060S got fewer checks (see `docs/OPT_CHATFIX.md`).
- Bug fixed on the way: the first span after a cache capture or hit read stale ring and conv state (read slot different from write slot). The programs now copy the state (`inkling_fork_state`). A hit now gives the same tokens as a cold run (24 of 24 prompts on the R9700 for Q4).
- Tool calls: the policy accepts a `tool` message that has only `tool_call_id`, an assistant message with `name` and tool calls, the role `developer` (rendered as system), an assistant `reasoning` string in place of `reasoning_content`, and unknown `chat_template_kwargs` keys. These differ from the Jinja template on purpose. `tool_choice` `none` removes the tool declaration. `required` and a named function are soft: the prompt ends with a system message that asks for a tool call, and a named function declares only that tool (3 of 3 live cases called a tool; no grammar). Arguments are sent whole in one stream delta.
- Checks: the OpenAI-style tool probe passes 55 of 55 on both GPUs; the agent gate passes without `name` in the tool messages (6 turns, 0 failing); consistency, agent, golden and compare gates pass; the sampling gate fails only on the two greedy checks as before.
- Gaps that need a loom-serve change (issue texts in `docs/OPT_CHATFIX.md`): `function.arguments` as a JSON object and a missing call `type` are rejected by the runtime; the policy cannot see the call name of a tool message, so the name header the template prints is not rendered; the prefix cache keeps only chunk frontiers (a 5,133 token prompt caches 4,096); no rewind of generated tokens, so the generated state is not reused when the client drops the reasoning.

## 14. loom-serve patches

This repository holds only the package (programs, card files and `patches/`); the tools, tests and measurement logs are not part of it. The `patches/` folder holds three small loom-serve patches for tool calling (open as pull requests in ROCm/hrx-system): tool call `arguments` as a JSON object (#3551), a missing tool call `type` means `function` (#3552), and the function name on tool messages (#3554). The package works without them: its chat policy accepts the same requests and prints a nameless tool header. With the patches applied, a client that sends `arguments` as an object or omits `type` no longer gets HTTP 400 from loom-serve, and tool messages carry the name as the template prints it. See `patches/README.md`.

Open loom-serve limits that need runtime work and have no patch yet: hard enforcement of `tool_choice` required and named functions (#3556), prefix-cache capture at the end of the prompt (#3555), and reuse of generated state when a client drops `reasoning_content` (#3557).
