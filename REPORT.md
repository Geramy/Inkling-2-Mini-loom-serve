# Inkling-2-Mini for AMD Loom: measurement report

How the values on this repository's model card were measured. Generated from `info.json` (schema `loom-card/3`) by the loom-skills card generator; the card's README.md is rendered from the same data.

## Setup

- Package: this repository. Programs generated by loom-skills `618f89e` with hrx-loom `0.3.0` (hrx-system commit unknown).
- Checkpoint: [unsloth/Inkling-2-Mini-GGUF](https://huggingface.co/unsloth/Inkling-2-Mini-GGUF) @ `ea0c79b2ecd73669e774c8519b79bfabfddbc027`, `Mainline_Support/Inkling-2-Mini-UD-Q4_K_XL.gguf_file`, sha256 `e64276656f072e9b2197a61723667cbdb71da66a716ffd966e572c21088f3cd3`.
- Programs measured: the sha256 below is card_lib.programs_sha256, over `program/*.loom` without each file's first-line generator comment.

## Method

- `perf.py` (loom-benchmark) sends real-text requests: a short prompt for decode, decode after 2k and 32k tokens of context, and prefill of documents of about 1k, 2k, 8k, 16k and 32k tokens. Each run gives one value per metric; the card shows the median over the sessions of each session's median sample (a session without an "aggregate" key was measured as the mean of its runs: its row says so).
- `c4_steady.py` runs 4 concurrent streams and reports the aggregate decode rate over the window in which all 4 are decoding; the card shows the median of the runs.
- One engine runs at a time on the same machine, with the same GGUF. Loom rates are timed by the client; llama.cpp rates come from its server-side `timings`.
- Every performance value comes from a `devlab-perf` job (loom-skills) on an AMD DevLab Dispatch Strix Halo or R9700 runner: Loom, served with the active wait (`--device=amdgpu://?completion_spin_ns=4294967295`), and llama.cpp on the same runner, with the published programs.
- Drafted tokens accepted is the `spec` gate's count: accepted over proposed draft tokens across its requests.
- Gates are loom-benchmark's `gates.sh` at the LEVEL shown; DevLab runs are the nightly-gates workflow on AMD DevLab Dispatch.
- Roofline: per metric, the rate at the hardware limit computed from the GGUF's tensors by loom-roofline `roofline.py`: decode is memory bandwidth / bytes read per token (weights, active experts, KV cache), prefill is peak FLOP/s / flops per token, 4 streams reads the weights once for 4 tokens. With speculative decoding, decode and 4 streams are verify passes per second x (1 + acceptance x depth) tokens per pass, with the acceptance measured in the row's own session (loom-serve's drafted-token counters around perf.py's decode request, or around c4_steady.py's streams), else the `spec` gate's.
