## Part A: history cache

### What the runtime does (measured, loom-serve 0.3.0)

- Retained rows: an idle row keeps the state of its last conversation (prompt plus generated tokens). A new request reuses it only if its prompt is an exact extension of that history. `cached_tokens` is then almost the whole previous prompt (5333 of 5348). The policy marks the state reusable only when `complete_text` shows that the generated bytes equal the canonical rendering (CHAT_POLICY section 4). With `rows` 4, six conversations used round-robin thrash the four rows (LRU, cyclic access): `cached` was 0 for all six follow-ups even with the reasoning echoed.
- Prefix cache (`prefix_cache_capacity`): endpoints captured at prefill chunk boundaries. Measured: a hit is always a multiple of `prefill_capacity` (2048 here; 512 gives multiples of 512). The last partial chunk of the previous prompt is recomputed. Entries are found by common prefix, so a second conversation that shares only a system prompt also hits. Hits across conversations and forks work.
- Session cache (`session_cache_capacity`): serves explicit sessions (`X-Loom-Session`, `/v1/sessions`). The metric `session_cache_endpoints` stayed 0 in all our automatic traffic. Left at 0.
- Why no echo means no reuse: the model writes `<|message_model|><|content_thinking|>R<|end_message|><|message_model|><|content_text|>T<|end_message|>`. A client that sends back only `content` makes the next prompt `...<|message_model|><|content_text|>T...`, which differs from the retained state at the thinking block. Rewinding the state to the common prefix is not an operation of the runtime (known SDK limit, `loom-kb/topic/sdk.md`, "generated prefixes are not automatically checkpointed", loom-skills issue #40). We did not change the template or the generated tokens to force a hit.

### Cache correctness (found and fixed: a state bug, not noise)

Method: `chat_numerics.py` sends 24 fixed prompts (about 5.5k tokens each), every prompt three times in a row (cold, then two hits), greedy, 40 output tokens, and compares the texts across server configurations; `chat_cache_correct.py` sends a fixed sequence of 16 greedy requests (conversation, follow-up, fork, second conversation sharing only the system prompt, unrelated conversation, four eviction requests, repeats) against a cache-off server and cache-on servers (capacity 16 and 2). Fixed assistant history, so every request is a function of the script.

Before the fix (with the cache on):

| Comparison | Result |
|---|---|
| cache off, prefill 2048 against prefill 1024 (two chunkings) | identical 24 of 24 (the pipeline is chunk invariant to the bit) |
| cache off against cache on (16), first run of each prompt (cached 0) | identical 4 of 24; first differences at characters 16 to 129 (as early as the 4th token) |
| repeats of a prompt against its own first run, cache on | equal in 13 of 48; cache off 48 of 48 |
| bisect (repeat of one request): cache 0 with `transient_bytes` raised, cache 0 with 8 checkpoints | identical to the base (373 chars): memory hints and slot count are not the cause |
| cache capacity 1 / 16 | three different outputs (367 / 361 chars) for capacity 0 / 1 / 16, each stable per capacity: the capture schedule changes the result |

Because the cache-off pipeline is bit-exact across chunkings, a difference at the 4th token is not reduction-order noise. Cause found by reading the dispatch: `dispatch/spans.loom` gives the first span after a fork (a prefix capture or a restore) a read slot (the anchor) different from its write slot. `kernel/mix` conv commit honours read and write, but the attention kernels (`kernel/attn`: local ring, dynamic conv rows) use the write slot only; `KERNELS_attn.md` said "a fork copies the slot, so read = write", and loom-serve 0.3.0 does not copy. After every capture and every hit the next span attended to a stale or empty window. The effect is small for the answer (global layers keep the context) but visible as flipped early tokens.

Fix: `inkling_fork_state` copies the whole recurrent region of each such span from its read slot to its write slot once, right after the span table is built (1024 x spans workgroups, all exit at once unless the slots differ). After the fix:

| Comparison | Result |
|---|---|
| cache off against cache on (16), first run of each of the 24 prompts | identical 24 of 24 |
| repeats (hits of 2048 or 4096 tokens) against their own first run | equal 48 of 48 |
| 16-request sequence, 96 tokens, cache off against capacity 16, and against capacity 2 (real eviction, hits of 0, 2048 and 4096 tokens, fork, shared system prompt) | identical 16 of 16 in both |
| 8060S, cache on, 6 prompts | hit equals cold, 6 of 6 |
| 8060S Q8 (prefill 512, hits of 1024 and 3072) and R9700 Q8 | hit equals cold, 4 of 4 and 6 of 6 |

So a hit now gives the same tokens as a cold recompute, bit for bit, on the greedy path, after eviction, for a fork and for a conversation that shares only the system prompt. The comparison is on tokens: the chat route has no logprobs (rejected by the policy, not offered by the sampler), so NMSE and top-2 gaps cannot be read; with bit-identical tokens over 40 to 96 greedy steps, 40 requests and two GPUs, that is the strongest statement the route allows. The regression tests are `scripts_CHAT/chat_numerics.py` (cache on against off, hit against cold) and `chat_cache_correct.py` (sequence with eviction); both need a live server. The bug also affected explicit checkpoint forks and any future fork use of the package, not only the prefix cache.

Cost of the fix: `ab_session.py` (R9700, median of 3, tok/s): see the table "Performance guard" below.

Other cache findings:

- Echo plus retained row is unchanged and still works with tool calls (loop6 with echoed reasoning: cached 203 of 228, 270 of 295, 324 of 349, ...).
- `reasoning` (alias of `reasoning_content`, used by OpenRouter, newer vLLM and several UIs) is now read by the policy from the message, so those clients get the retained-row reuse too (see policy changes).
- Not changed: history rendering. The thinking block is rendered exactly as the client sent it; dropping reasoning in history is the client's choice (CHAT_POLICY section 4 stands).

### Policy changes (all in `package_CHAT/control/chat.loom`; each differs from the template and is deliberate)

1. Role `developer` renders as `system` (the template raises). Error text now lists developer.
2. A `tool` message without `name` is accepted and rendered `<|message_tool|><|content_text|>...` (the template looks the name up by `tool_call_id`).
3. An `assistant` message with tool calls ignores its `name` (the template prints it on text pieces when it equals the call name and raises when it differs).
4. The assistant `reasoning` string is used when `reasoning_content` is absent or empty.
5. `chat_template_kwargs` unknown keys are ignored (the known keys keep their checks and conflict rules).
6. `tool_choice` string `none` removes the tool declaration (`chat_begin`). `required` and a named function set state bit 22; `chat_end` then ends the prompt with the system message "The next assistant message must be a call of a declared tool. Do not answer in text."; a named function also keeps only that tool in the declaration.

Kit and tests: `kit_CHAT/chat_probe.py` models the policy (`INKLING_MODE`; `simulate` takes `tool_choice`) and `verify` keeps all template-exact checks, plus 44 policy checks against the template's own render of the equivalent messages (`chat_golden_policy.py` made 16 new golden cases: id-only, parallel id-only, mixed, developer, assistant name, reasoning alias, tool_choice none, required, named, kwargs). `$T -I kit/chat_probe.py GGUF --verify cfg.json`: base kit 219 OK; `kit_CHAT` 263 OK, 0 FAIL, 0 SKIP (219 template-exact checks unchanged, one of them now the template-names check of tool_id_only, plus 44 new). `kit_counts.py` (kit token count equals the live `/v1/chat/completions/input_tokens` for every golden case, 59 cases) 0 failing against the patched server. `test_template.py` counts mode against the patched server: 101 PASS, 0 FAIL (golden 59 cases; kwargs unknown-key cases moved from reject to accept). `test_options.py` (unknown kwargs key now accepted) and `test_output.py` run in `chat_run_all.sh` (see Verification). `chat_tool_probe.py` is the live regression set (needs a server).

## What still needs loom-serve or HRX changes, with issue text ready to file

1. Title: "Chat tool_calls: accept function.arguments as a JSON object". Repro: POST `/v1/chat/completions` with an assistant message `{"role":"assistant","content":null,"tool_calls":[{"id":"call_1","type":"function","function":{"name":"get_weather","arguments":{"city":"Paris"}}}]}` followed by a tool message. Actual: HTTP 400 "chat field 'arguments' expects JSON type string". Expected: accepted. llama.cpp, vLLM and several clients send an object; the Inkling policy already parses either form.
2. Title: "Chat tool_calls: default type to function". Repro: the same message with `tool_calls[0]` lacking `"type"`. Actual: HTTP 400 "assistant tool_calls must be functions". Expected: accepted (the only defined type; the OpenAI SDK always sends it, some agents omit it).
3. Title: "Text policy ABI: give chat_message the tool name for a tool message". Repro: send a tool message with only `tool_call_id` (the OpenAI standard). Actual: the policy sees one message and a 64-bit state, so it cannot print the function name that the chat template prints (`<|message_tool|>NAME`); our policy renders the header without a name. Expected: an extra argument (the name of the call with that id, or the earlier calls as id and name pairs) so a package can match its template exactly.
4. Title: "Prefix cache: capture the prompt-end state, not only chunk boundaries". Repro: a 5,133-token prompt with `prefill_capacity` 2048 and `prefix_cache_capacity` 16; the follow-up reports `cached_tokens` 4096. Expected: 5133 (the full previous prompt). Also document `prefix_cache_capacity` (one endpoint per chunk frontier, a 171.6 MB state slot each for this model, pool pages shared) and that `session_cache_capacity` serves only explicit `X-Loom-Session` sessions.
5. Title: "Fork slot contract: document the read-slot semantics for text programs". The first span after a fork carries a read slot different from its write slot and the runtime does not copy the slot, so every program with in-place recurrent or ring state must copy. Our package now does (`inkling_fork_state`); the library documentation should say it (found as wrong output after every prefix-cache capture).
6. Title: "Generated-token checkpoints or common-prefix rewind" (loom-skills issue #40): clients that drop `reasoning_content` cannot reuse the generated state; the prefix cache reuses only the prompt side.

## Not done and limits

- `tool_choice` `required` and a named function are soft: one demanding system message plus, for a named function, a one-tool declaration. A strict guarantee needs a grammar or a token set in the sampler (loom-serve change; the sampler excludes one token, and excluding the text token made the model stop without a call).
- Arguments are emitted whole (one SSE delta per call), not in fragments.
- The policy differences listed above are deliberate; the exact template name lookup needs issue 3.
- No logit-level comparison (the route offers no logprobs); equality is bitwise on tokens.
- The published card changes only after `publish_build.py` is run and the card is republished.
